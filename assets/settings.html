    Dispatch

    Open Dispatch

    Added to Dispatch's prompt for every conversation and followed before its own defaults. Use it for where your repositories live, which machine suits which work, branch naming, and anything you find yourself repeating.

    The agent that reads your messages and proposes steps, with only Yardbell's tools, and the model it runs. Each agent keeps its own model. Your approval setting and rules work the same on both. A conversation stays on the agent it started on, so a new agent applies to new conversations, while a new model applies from the next message.

    Each step shows up in the conversation as a card. When Dispatch asks, you can approve it, edit it first or reject it, and nothing runs until you approve. A change to Dispatch's memory always asks, even when this is set to go ahead, unless a rule for it says otherwise.

    Rules

    A rule decides the steps it matches instead of the setting above. Deny always wins. Otherwise the rule that names the most of step, machine and folder wins, so their order does not matter. A folder is a name from the folder list, like acme/web, or a path, and covers the folders inside it. Use * for any part of a name.

      Dispatch runs Claude Code on this machine. The agent it starts can be any of yours.

            Worktree setup

            A command that runs in each new worktree Yardbell creates for a repository, before the agent starts, such as bin/setup, npm ci or cp "$YARDBELL_MAIN_CHECKOUT/.env" .. The folder is the repository's main checkout, as in the folder list or as a path, and * matches any part of a name. If the command fails or runs past its timeout, the agent starts anyway, the session shows the output, and the agent is told.

            Only commands saved here run. A repository's own script runs only when you name it here, like .yardbell/setup, because that script comes from whatever branch is checked out.

              The command runs through your login shell in the new worktree, with the main checkout's path in $YARDBELL_MAIN_CHECKOUT.

              Connections

              The tools your pipelines and agent sessions can reach.

              How connecting works
              1. Press New connection and pick your tool. If it is not listed, add it with the address of its MCP server. The tool's docs give the address.
              2. Sign in with your account. Your browser opens the tool's own page, where you approve what Yardbell may do. There is no token to create or paste.
              3. That is it. Yardbell checks the connection and lists what it can do. Press Test to check again at any time. It changes nothing.

              Pipelines use a connection in a trigger or a step. Agent sessions get every MCP connection too, and sign in to it themselves on their own machine. Use a token only for a tool with no MCP server.
